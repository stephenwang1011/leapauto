# 蓝牙钥匙保守改进方案

> 文档状态：方案评审稿，尚未实施  
> 编写日期：2026-09-27  
> 代码基线：`3.6.46`（versionCode `3006046`）  
> 适用模块：蓝牙数字钥匙、后台无感钥匙、车辆配置同步、连接诊断，以及实验性的直进直出入口
>
> **当前状态更新**：直进直出生产入口、EEED/EEE2 控制器和相关命令已从 App
> 完整移除。本文中的直进直出内容仅保留为历史研究与安全评审记录，不表示当前可用。

## 1. 目的

当前用户已确认：现有版本的蓝牙钥匙在其当前手机与车辆组合上可以使用。因此，后续改进必须优先保护已经成功的实车链路，不能因为静态文档、车型推断或单元测试结论，直接替换当前已经被车辆接受的协议版本、认证文本、加密过程或配置字段。

本方案的目标是：

1. 冻结并保护当前已经成功的蓝牙认证与控锁链路。
2. 先修复不影响车端报文的 UI、诊断、隐私和状态表达问题。
3. 把“请求已发送”“车辆已确认”和“车辆实际执行”分开表达。
4. 为多车型建立按车辆保存的最后成功协议档案，避免升级后自动改变协议。
5. 将直进直出从普通蓝牙钥匙中隔离，在安全闭环完成前保持实验状态。
6. 每次只交付一个可回退的小批次，通过同一台手机、同一辆车回归后再继续。

本文档是实施方案，不表示下列项目已经开发、测试、打包或通过实车验收。

## 2. 当前证据与边界

### 2.1 已确认事实

- 用户确认当前蓝牙钥匙在其当前手机与车辆组合上可以使用。
- 当前普通蓝牙钥匙使用 FFFE 服务和 FFF2 特征，代码入口为：
  - `app/src/main/java/com/leapauto/app/bluetooth/BluetoothKeyController.kt`
  - `app/src/main/java/com/leapauto/app/bluetooth/BleKeyProtocol.kt`
- 当前连接路径固定选择 `BleCompatibilityProfile.ONE_PAO_V010`。
- 当前 C10/C16 路径倾向使用协议小版本 9，并在部分后台恢复路径中把已保存的小版本升级为 9。
- 当前代码已经包含完整认证、快速重连凭证、命令 3 配置同步、后台前台服务和开机恢复。
- 设置页蓝牙入口具有“点击设置标题 5 次后显示”的隐藏逻辑。
- 当前主界面仍存在可直接打开蓝牙管理页的蓝牙状态按钮。
- 当前直进直出界面调用的是普通云端控车 `cmdid=150`，新增的 EEED/EEE2 BLE 协议辅助代码没有接入生产 GATT 调用链。

### 2.2 尚未确认的事实

用户所说“蓝牙钥匙可以使用”当前只能证明实际使用过的路径成功，不能自动扩大为以下全部能力都已验证：

- 冷启动后的自动恢复是否稳定。
- 开机广播拉起后台服务是否稳定。
- 靠近自动解锁和远离自动锁车是否均已实车确认。
- 微动开关的第 4 个配置字段表示“能力”还是“用户开关”。
- 命令 3 配置是否在所有车型上都会返回明确回执。
- C10、C16 之外的车型是否接受 `ONE_PAO_V010`。
- EEED/EEE2 直进直出服务是否已被目标车辆接受。

以上项目必须通过脱敏诊断和现场测试分别确认，不能从“手动蓝牙锁控成功”推导得到。

### 2.3 文档差异

`API/BLUETOOTH_FIELD_TEST.md` 仍以 `3.3.34` 的失败结果为开头，已经不能代表当前 `3.6.46` 的实车状态。实施第一批改进时应同步更新该文档，但必须保留旧日志为历史证据，并明确区分：

- 历史失败版本与结果。
- 当前用户确认成功的版本和功能范围。
- 尚未执行的现场测试项。

## 3. 不破坏现有功能的硬性约束

### 3.1 第一阶段禁止修改的内容

在完成当前成功基线采集前，不得修改：

- `BleKeyProtocol.createSession()` 的密钥派生。
- P-256、SM2、SM3、SM4、AES 的算法选择和字节顺序。
- `BleKeySession.buildAuthentication()` 生成的认证文本和外层报文。
- 当前成功路径中的 `ONE_PAO_V010` 选择。
- 当前成功车辆使用的协议小版本。
- 当前认证和配置的标定参数字节。
- FFFE、FFF2、CCCD UUID。
- 当前 MTU 请求值、已验证的分片上限和写入顺序。
- 当前成功绑定的设备地址、证书指纹和快速重连凭证作用域。
- 已保存用户配置的迁移值。

### 3.2 兼容迁移约束

- App 升级不能删除已经成功的绑定。
- App 升级不能把已有 `desired`、`applied`、标定参数或协议版本重置为新默认值。
- 新增字段必须有向后兼容默认值。
- 读取旧记录失败时应暂停后台钥匙并提示重新确认，不能静默创建一套不同协议的新绑定。
- 任何协议自动切换都必须有明确证据和可回退记录。
- 不能以车型字符串覆盖已经成功保存的车辆级协议档案。

### 3.3 实车安全约束

- 未经用户明确授权，不发送真实车辆命令。
- GATT 写入成功只代表 Android 完成写入，不代表车辆接受或执行。
- HTTP 接口返回成功只代表服务端接受请求，不代表车辆已执行。
- 只有匹配当前请求的车辆事件或后续可信车辆状态，才能显示“已确认”或“已完成”。
- 直进直出在停止闭环完成前不得作为可用功能交付。

## 4. 改进批次总览

| 批次 | 范围 | 是否改变车端报文 | 风险 | 交付前提 |

| 0 | 冻结当前成功基线 | 否 | 低 | 用户确认当前可用版本 |
| 1 | UI、诊断、隐私、系统状态 | 否 | 低 | 批次 0 完成 |
| 2 | 配置同步状态机 | 否，保持原始配置字节 | 中低 | 批次 1 实车无回归 |

## 5. 批次 0：冻结当前成功基线

### 5.1 目的

建立可以回退和逐字节比较的已知可用版本。后续任何改动必须证明没有改变这条链路，或者明确说明为什么需要改变。

### 5.2 需要保留的交付物

- 当前签名 Release APK。
- APK 的 SHA-256。
- APK 签名证书摘要和签名方案。
- 当前版本号和 versionCode。
- 当前成功车辆的脱敏诊断报告。
- 当前使用的车型名称、Android 版本和手机厂商，不记录 VIN、完整 MAC、证书或 PIN。
- 当前成功路径属于完整认证 `AA AE` 还是快速重连 `AA EE`。
- 实际选择的协议小版本及其来源：车辆广播、已保存绑定或默认值。
- 当前兼容策略名称。
- 当前标定参数四元组。
- 当前用户开关和实际发送配置位的脱敏摘要。

### 5.3 建议新增的基线记录结构

该结构只描述后续实现目标，不要求第一批立即修改持久化：

```text
KnownGoodBleProfile
  scopeHash                  账号、车辆、设备和证书作用域的不可逆摘要
  protocolMinor             最近一次成功认证使用的小版本
  protocolMinorSource       advertised / saved / default / migrated
  compatibilityProfile      ONE_PAO_V010 / LEGACY
  authenticationMode        full / reconnect
  calibration               4 项原始参数
  transmittedFlags          实际发送的 2 位或 4 位摘要
  authenticatedAt           最近成功时间
  appVersion                产生成功记录的 App 版本
  schemaVersion             档案格式版本
```

禁止保存认证原文、证书文本、会话密钥、IV、PIN、VIN 明文或完整蓝牙地址。

### 5.4 基线通过标准

- 当前 APK 可以重新安装或覆盖安装。
- 同一手机、同一车辆能复现当前成功路径。
- 已保存绑定在重启 App 后仍可加载。
- 诊断信息足以识别协议选择，但不包含个人车辆数据和密码材料。
- 当前 APK 可在后续版本回归时立即回退。

## 7. 批次 2：配置同步状态机

### 7.1 当前问题

当前 `BluetoothKeyController.configure()` 在下列情况下可能调用成功回调：

- 等待车辆确认超时。
- 构造或发送配置报文抛出异常。
- 配置期间收到任意 `EVENT`。

成功回调会使 `BleKeyRuntime` 把 `desired` 写入 `applied`。这会把“已发送”或“链路仍活跃”错误地记录成“车辆已确认”。

### 7.2 目标状态机

```text
IDLE
  -> REQUESTED              用户保存并通过 PIN 确认
  -> WRITING                开始写入命令 3
  -> DELIVERED_UNCONFIRMED  Android 已完成全部分片写入
  -> CONFIRMED              收到匹配命令 3 的 0/00 回执

任何阶段
  -> REJECTED               收到匹配命令 3 的明确失败回执
  -> SEND_FAILED            构造失败或 GATT 写入失败
  -> CONFIRMATION_TIMEOUT   写入完成但等待回执超时
```

状态约束：

- 只有 `CONFIRMED` 可以更新 `applied` 和 `confirmedRevision`。
- `DELIVERED_UNCONFIRMED` 允许连接回到 `READY`，但 UI 必须显示“已发送，车辆未确认”。
- `CONFIRMATION_TIMEOUT` 不主动断开已认证连接。
- 普通锁控事件不能确认配置。
- 拒绝事件必须先解析，再决定配置状态，不能在解析前把配置标记为成功。
- 同一连接仍只允许一条无请求 ID 的配置命令。

### 7.3 防止未确认配置反复发送

如果只取消“静默确认”，后台可能在每次连接后重复发送配置。需要同时增加：

- `lastDeliveredRevision`：最近完成写入的配置版本。
- `lastDeliveredAt`：最近发送完成时间。
- `lastConfirmationState`：confirmed、unconfirmed、rejected 或 failed。
- 单连接最多发送一次命令 3。
- 未确认配置设置冷却时间，不能立即连续重发。
- 用户主动点击“重新同步”可以越过冷却时间，但仍需 PIN 和确认弹窗。
- 配置内容变化后产生新 revision，旧 revision 的回执不能确认新配置。

### 7.4 回调拆分

控制器与运行时之间不再只使用一个模糊的 `onConfirmed` 回调，建议拆分为：

```text
onConfigurationWriteCompleted(revision)
onConfigurationConfirmed(revision)
onConfigurationRejected(revision, resultCode)
onConfigurationUnconfirmed(revision, reason)
```

运行时只在 `onConfigurationConfirmed` 中更新 `applied`。

### 7.5 涉及文件

- `app/src/main/java/com/leapauto/app/bluetooth/BleConfigurationTracker.kt`
- `app/src/main/java/com/leapauto/app/bluetooth/BluetoothKeyController.kt`
- `app/src/main/java/com/leapauto/app/bluetooth/BleKeyRuntime.kt`
- `app/src/main/java/com/leapauto/app/bluetooth/BleManagedKey.kt`
- `app/src/main/java/com/leapauto/app/ui/BluetoothPassiveSettings.kt`
- 相应 JVM 单元测试

### 7.6 必测场景

- 写入完成，收到命令 3 成功回执。
- 成功回执早于最后一个分片写入回调。
- 写入完成，没有回执并超时。
- 写入中收到普通锁控事件。
- 写入中收到拒绝事件。
- 写入异常。
- 配置变化后收到旧 revision 回执。
- 断线后收到迟到回调。
- 未确认配置重连时不形成发送风暴。
- 关闭后台总开关未确认时，后台服务保持必要的同步机会，但 UI 不显示已关闭。

## 8. 批次 3：最后成功协议档案

### 8.1 目的

当前实车成功配置应按车辆保存，后续版本不得仅根据车型名称重新决定协议。该机制用于保护当前成功车辆，同时为其他车型保留独立适配空间。

### 8.2 协议选择顺序

建议分为“已有成功绑定”和“首次绑定”两条路径。

已有成功绑定：

1. 作用域、证书指纹和设备地址匹配的最后成功协议档案。
2. 当前广播明确携带且与档案兼容的新版本，仅记录为候选，不在后台静默替换。
3. 用户明确选择重新绑定后，才进入首次绑定流程。

首次绑定：

1. 当前扫描记录明确携带的协议小版本。
2. 同一完整作用域下曾成功的档案。
3. 经过实车确认的车型级兼容表。
4. 没有任何证据时使用保守默认值，并明确记录来源。

### 8.3 禁止的自动行为

- 不能因为车型名称包含 C10 或 C16，就覆盖已成功保存的小版本。
- 不能因为一次认证失败就在 8 和 9 之间自动高频重试。
- 不能在后台自动从 `ONE_PAO_V010` 切换到 `LEGACY`。
- 不能把另一个账号、VIN、deviceId、证书或 MAC 的成功档案复用到当前车辆。
- 不能因为云端 `controllerVersion` 是 `2.0` 就直接推导 BLE minor。

### 8.4 失败与回退

- 当前档案认证成功：刷新成功时间，不改变档案内容。
- 当前档案认证失败：保留档案，记录失败阶段和原始结果码。
- 连续失败达到阈值：暂停后台重试并提示用户在车辆旁重新扫描，不自动迁移协议。
- 用户重新绑定成功：原子替换档案，并保留上一个档案的非敏感回退摘要。
- 新档案失败：恢复上一个成功档案。

### 8.5 测试要求

- 旧绑定升级后逐字段保持不变。
- 广播版本不能静默覆盖成功档案。
- 作用域任意一项变化都不能复用档案。
- 失败不会清除当前成功档案，除非证书明确失效或用户解除绑定。
- 多车型测试不共享兼容策略状态。

## 9. 批次 4：微动开关与配置字段验证

### 9.1 当前不确定性

当前代码同时存在三类概念：

- 用户偏好：`buttonEnabled`。
- 车辆能力：`supportsButton`。
- 云端配置：`bleKeyBtn`。

`ONE_PAO_V010` 的认证文本、命令 3 配置和后台快速重连对第 4 位的处理并不完全等价。因此不能直接认定当前开关一定无效，也不能直接把能力位改成用户偏好位。

### 9.2 先增加的只读证据

不记录字段内容之外的敏感信息，只记录以下布尔摘要：

```text
用户总开关
用户自动解锁
用户自动锁车
用户微动开关
车辆能力是否确认
认证实际发送的配置位
命令 3 实际发送的配置位
快速重连实际发送的配置位
云端配置保存结果
车辆命令 3 回执结果
```

### 9.3 实车验证矩阵

| 总开关 | 自动解锁 | 自动锁车 | 微动 | 观察目标 |
| --- | --- | --- | --- | --- |
| 关 | 关 | 关 | 关 | 后台功能均不执行 |
| 开 | 关 | 关 | 关 | 仅维持钥匙，不触发被动操作 |
| 开 | 开 | 关 | 关 | 靠近行为 |
| 开 | 关 | 开 | 关 | 远离行为 |
| 开 | 关 | 关 | 开 | 实体微动开关行为 |
| 开 | 开 | 开 | 开 | 组合行为和优先级 |

每次只改变一个变量，记录认证模式、实际发送位、命令 3 回执和车辆实际行为。

### 9.4 证据确认后的实现选择

如果第 4 位被证明是车辆能力：

- `supportsButton` 由车辆档案提供。
- UI 的微动开关偏好通过云端或另一个已验证字段表达。
- 能力未知时 UI 不宣称支持。

如果第 4 位被证明是用户开关：

- 认证、命令 3、快速重连统一使用 `enabled && buttonEnabled`。
- 能力判断只决定开关是否可编辑，不直接替代用户选择。

在证据确定前，保持当前成功车辆的报文不变。

## 10. 批次 5：直进直出隔离方案

### 10.1 当前状态

- `BleStraightProtocol.kt` 定义了 EEED 服务、EEE2 特征、认证和控制报文辅助方法。
- 生产代码没有建立 EEED GATT 会话，也没有订阅 EEE2 通知。
- 当前界面实际调用普通云端 `cmdid=150`。
- 当前停止指令与其他云端请求共用单线程队列。
- 当前界面本地状态会在车辆确认前显示移动中。
- 当前没有覆盖 Activity 进入后台、进程终止和网络阻塞的可靠停止闭环。

因此，当前实现不得以“蓝牙直进直出已完成”交付。

### 10.2 隔离要求

- 直进直出默认关闭，并由独立实验开关控制。
- 不在普通蓝牙钥匙设置、主页快捷命令或后台自动钥匙中默认展示。
- 不复用普通锁控的 `READY` 作为直进直出可用条件。
- 不把普通 FFFE/FFF2 认证成功等价为 EEED/EEE2 已认证。
- 不硬编码真实 VIN 作为授权机制。
- 直进直出故障不能覆盖普通蓝牙钥匙绑定、凭证或配置。

### 10.3 独立状态机

```text
DISABLED
  -> DISCOVERING_EEED
  -> SUBSCRIBING_EEE2
  -> AUTHENTICATING
  -> WAITING_FOR_VEHICLE
  -> READY
  -> MOVING_FORWARD / MOVING_BACKWARD
  -> STOPPING
  -> READY

任何阶段
  -> PAUSED / UNAVAILABLE / FAILED / DISCONNECTED
```

只有车辆最新通知明确为 `READY`，并且通知时间在允许窗口内，移动按钮才可用。

### 10.4 停止指令硬性要求

- STOP 使用独立高优先级发送路径，不能排在前进或后退请求之后。
- 手指松开时发送 STOP。
- 指针取消或移出时发送 STOP。
- 抽屉关闭时发送 STOP。
- Compose 组件销毁时发送 STOP。
- Activity `onPause`、`onStop` 时发送 STOP。
- 蓝牙断开前尽最大努力发送 STOP。
- 移动开始后启动本地看门狗；未持续收到新鲜车辆状态时发送 STOP 并禁用按钮。
- 只有车辆回报停止状态后显示“已刹停”。
- STOP 发送失败时显示明确故障，并要求用户立即人工接管，不能显示成功。

### 10.5 直进直出测试门禁

在实车测试前必须完成：

- 独立 GATT 假实现的全状态机测试。
- STOP 抢占测试。
- UI 松手、取消、销毁、后台切换测试。
- 通知过期测试。
- 断线测试。
- 错误状态和拒绝码测试。
- 不影响普通蓝牙钥匙的回归测试。

首次实车测试必须在封闭、空旷、无人员和障碍物环境，由用户明确授权并在车辆旁人工监护。该授权只适用于当次明确操作，不能用于后台自动测试。

## 12. 实车回归矩阵

### 12.1 每一批都要执行的最小回归

1. 覆盖安装后旧绑定仍存在。
2. 打开 App 后蓝牙证书和绑定状态正常。
3. 手动扫描能够找到目标车辆。
4. 完整认证成功。
5. 快速重连成功；如果当前车辆没有快速重连，则记录为未覆盖。
6. 蓝牙手动解锁收到匹配车辆事件。
7. 蓝牙手动上锁收到匹配车辆事件。
8. 连接失败后能够恢复，不清除有效档案。
9. 切换前后台不会错误显示成功。
10. 退出登录后不复用旧账号绑定。

### 12.2 后台钥匙回归

1. 总开关关闭时不自动启动后台钥匙。
2. 总开关开启且配置已确认时启动前台服务。
3. 息屏后服务状态可见。
4. 车辆离开范围后不会形成快速重连风暴。
5. 车辆重新出现后可以恢复连接。
6. 手机重启后仅在满足全部条件时恢复。
7. App 覆盖升级后保持旧绑定和用户开关。
8. 厂商省电策略阻止后台时给出准确提示，不承诺一定可用。

### 12.3 被动行为回归

- 靠近自动解锁单独验证。
- 远离自动锁车单独验证。
- 微动开关开启和关闭分别验证。
- 自动操作与手动蓝牙锁控不会并发冲突。
- 自动操作与云端主页控车不会同时发送相反动作。
- 每个行为记录车辆实际结果，不能只记录 GATT 写入完成。

## 13. 发布与回退策略

### 13.1 小批次发布

- 每个批次独立提升版本号。

- 旧绑定丢失或被重置。
- 后台服务出现重复连接风暴。
- 用户关闭的设置被自动打开。

- 蓝牙失败后错误地发送云端控车命令。
- 退出登录后仍能访问旧车辆蓝牙绑定。

- 上一版本应用数据结构版本。

## 16. 实施前待确认项

以下问题不阻塞批次 1，但会影响后续批次：

## 17. 推荐实施顺序

1. 完成批次 0，冻结当前成功 APK、签名和脱敏诊断。
2. 实施批次 1，只处理 UI、日志、隐私和系统状态。
3. 交付一个签名 Release，由同一手机、同一车辆执行最小回归。
4. 批次 1 通过后实施批次 2，修正配置同步状态机。
5. 配置同步实车确认后实施批次 3，保存最后成功协议档案。
6. 采集微动开关对照证据后再决定批次 4 的字段语义。
7. 直进直出始终独立开发，在 STOP 安全闭环前保持隐藏和禁用。

该顺序将当前可用的蓝牙钥匙作为不可破坏的基线，优先消除不改变车端报文的问题，再逐步处理状态一致性和车型兼容，避免一次性重构导致已经成功的车辆重新出现认证失败。
